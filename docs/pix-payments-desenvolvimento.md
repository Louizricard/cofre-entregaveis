# Pix conectado pela Payments API — decisão e ensaio

14/10/2026. Preparação autorizada após duas recusas Orders (401 e, com perfil APP_USR de usuário de teste, 422). OAuth e identidade foram confirmados nas duas tentativas. Não há causa específica comprovada para o 422: o corpo não foi persistido e a allowlist não reconheceu enum. Não declarar que Orders não suporta OAuth apenas por essa resposta.

## Decisão técnica

Usar **Payments API para a próxima prova isolada**, mantendo o ensaio Orders e suas evidências. A [integração oficial de marketplace](https://www.mercadopago.com.br/developers/pt/docs/checkout-api-payments/how-tos/integrate-marketplace) orienta usar o access token OAuth do vendedor no backend. O [guia de migração](https://www.mercadopago.com.br/developers/pt/docs/checkout-api-orders/resources/migrate-payments-to-orders) mantém Payments em funcionamento e alerta para não presumir paridade Orders nos fluxos marketplace/split. Esse alerta não prova a causa da nossa recusa. Como o Cofre não retém comissão no MVP, `application_fee` é omitido; não implementar split nem adicionar sponsor para tentar contornar erros.

O [guia Pix Payments](https://www.mercadopago.com.br/developers/pt/docs/checkout-api-payments/integration-configuration/integrate-pix) documenta POST `/v1/payments`, com valor numérico, payment_method_id pix, payer e X-Idempotency-Key. A [referência Payments](https://www.mercadopago.com.br/developers/pt/reference/online-payments/checkout-api-payments/create-payment/post) usa collector_id, moeda/valor e estados próprios. O [guia Webhooks](https://www.mercadopago.com.br/developers/pt/docs/checkout-api-payments/additional-content/your-integrations/notifications/webhooks) distingue tópico payment de orders, assinatura HMAC e consulta `/v1/payments/{id}`.

## Isolamento e configuração

- Nenhum import do banco, API financeira do produto, invoice ou download. Nenhuma liberação de arquivo.
- `.local/pix-oauth.env`: `MP_OAUTH_PAYMENT_ENABLED=1`, `MP_OAUTH_PIX_ENABLED=0`. Ambos 1 fazem o receptor recusar inicialização. Durante configuração do painel, `MP_OAUTH_ENABLED=0`; ativar somente após callback salvo e confirmação de que o vendedor de teste está pronto.
- Aplicação existente: selecionar API Pagamentos, manter PKCE e permissões existentes. Atualizar callback HTTPS `/oauth/callback`. Em Webhooks, selecionar Modo de teste e evento Pagamentos; atualizar URL `/webhooks/mercadopago`, sem redefinir assinatura nem habilitar produção. Não criar outra aplicação/chave por conveniência.
- OAuth usa perfil sandbox anterior (`test_token: true`); token.live_mode true é recusado. State único/PKCE, user_id esperado e GET autenticado `/users/me` com ID/MLB/test_user continuam obrigatórios. O ensaio repete a conferência de identidade antes do POST. Não usar token da aplicação como fallback.
- `.local/pix-payment-attempt.json` separado: api payments, UUID de idempotência, referência cofre-payment-UUID, vendedor/aplicação e paymentId numérico. Criar exclusivamente e fsync antes da primeira requisição. Corrupção, API/identidade divergentes falham sem substituir tentativa. Não importar ID ORD nem a chave/ref de Orders.
- Corpo fixo: 50.00 BRL, pix, e-mail sintético test@testuser.com e first_name APRO. Não assumir que APRO na Payments API Pix reproduz a aprovação automática documentada em Orders. O resultado real será conferido; pending é evidência de criação, nunca de quitação. Não expor ou pagar QR em banco real.
- Resposta/GET exigem collector_id esperado, referência exata, live_mode false explícito, BRL, valor 50.00, pix/bank_transfer e ID numérico seguro. application_id explícito não pode divergir; sua ausência na resposta legado não é suprida por inferência do sufixo do token. Vínculo da aplicação vem do fluxo OAuth e precisa ser confirmado operacionalmente; não é um campo garantido pela referência Payments.
- Fixar ID e persistir antes de habilitar handler. Repetir POST com corpo/chave idênticos e GET. ID já conhecido exige GET antes do POST. Perda de resposta mantém chave/ref. Nenhuma troca automática de chave para contornar recusa.
- Inbox separada `.local/pix-payment-inbox.json`: transporte HMAC, limite 16 KiB, freshness, data.id conhecido e user_id esperado. Exige type payment/live_mode false; nunca aceitar simulador produtivo. GET com token do vendedor valida finanças, nunca body.status. HTTP 200 após gravação durável; falha permite retry. Duplicata não faz GET nem restaura aprovação antiga após entrega de estorno. Estados, IDs e evidências não se misturam com Orders.
- `.local/pix-payment-evidence.json`: api, fase, booleanos de OAuth/idempotência/GET/webhook, estado, HTTP/enum allowlist e horário. Sem payload/descrição, token, refresh, código, verifier ou QR. Token somente em memória, limite 45 minutos e apagado no encerramento; túnel limitado a 60 minutos.

## Resultado e limites atuais

Implementação compilada; **64 unitários API passaram**, lint e typecheck passaram. Nove testes Payments cobrem OAuth sandbox, POST/GET idempotentes, identidade, validação financeira, falha de rede/recuperação, webhook/HMAC, estorno/replay, persistência, HTTP e isolamento de tentativas. Os testes de transporte Orders continuam passando após extrair o transporte comum; validação financeira permanece específica de cada API.

Somente preparação local. Nenhuma chamada real Payments nem autorização nova foi executada nesta etapa. Compatibilidade OAuth + Pix Payments, notificação legítima, aprovação, expiração, cancelamento e estorno reais de sandbox permanecem por provar. Produção também depende de requisitos de conta/chave Pix, elegibilidade desse modelo e tarifas confirmadas com Mercado Pago; não inferir que ativar credenciais resolve esses pontos. Gate F10 aberto.

Se for necessário consultar suporte, fornecer apenas método/rota, HTTP 422, horário 14/10/2026 23:14:30 UTC, IDs públicos da aplicação/teste quando solicitados e descrição do cenário OAuth + Orders de usuário MLB test_user. Não enviar token, Client Secret, código/state/verifier, corpo completo ou QR. Nenhuma mensagem ao suporte foi enviada automaticamente.
